# Alternative à Tricount : La Pince

**Conclusion (19/11/2026)** : aucune app existante ne convient ; le groupe développe la sienne, **La Pince**, une PWA open source sans compte, hébergée gratuitement sur Cloudflare (Workers et D1). Besoin, stack, hébergement et nom tranchés ; version 1 fixée (décision 10), démo sans usage réel ; modèle de données, synchronisation, organisation du repo, outillage, tests, environnements et livraison tranchés (décisions 11 à 17). Squelette du monorepo, outillage et cœur de calcul livrés (décisions 18 à 22) ; depuis le 19/11, l'agent avance seul sur les étapes 4 à 7 et fusionne ses PR, arrêt aux données réelles (décision 23), le code se déployant à chaque fusion sur `main` (décision 43) ; conversion Tricount et corpus anonymisé livrés le 19/11 (décision 26) ; serveur et import en local livrés le 19/11 (décisions 27 à 31) ; app PWA en ligne livrée le 19/11 (décisions 32 à 34) ; hors ligne et bout en bout livrés le 19/11 (décisions 35 à 38) ; détection d'une base restaurée par le téléphone livrée le 19/11 (décision 39) ; instance du mainteneur déployée avec le groupe de démo et guide d'auto-hébergement livré le 19/11 (décision 40) ; export frais relu et corpus de démo régénéré le 19/11 (décision 41) ; import des vraies données reporté par l'utilisateur le 19/11 (« je ne veux pas les vraies données pour le moment ») ; copie quotidienne de la base dans un repo GitHub privé décidée le 19/11 (décision 44) ; le groupe de démo en ligne porte le corpus anonymisé. Refonte des écrans choisie sur maquettes du 19 au 20/11, livrée en quatre PR en première version à itérer à partir du 23/11, la liste des dépenses d'abord (décision 49).

Contexte : l'utilisateur utilise Tricount depuis longtemps avec un groupe d'amis, frustré par « des fonctionnalités basiques que nous trouvons manquantes, des lenteurs, une app qui ne fonctionne pas super bien » (dit par l'utilisateur). Déclencheur : un bug Tricount, en cours le 16/11 (date de début non précisée), empêche les apps du groupe de se synchroniser (dit par l'utilisateur).

Impact : non estimable en euros (usage entre amis, gratuit). L'enjeu est la friction du partage des dépenses de 13 personnes (236 dépenses et 14 remboursements du 25/11/2025 au 16/11/2026, 9 609,80 € de dépenses) ; coût d'hébergement visé : 0 €.

## Besoin

Dit par l'utilisateur le 16/11 :

- Mobile first, iOS et Android, avec une vue desktop (Tricount n'en a plus).
- Voir facilement les dépenses qui me concernent ; notifications seulement pour celles-là (Tricount notifie tout le monde).
- Recherche correcte ; app rapide et fiable ; visualisation simple de qui dépense quoi.
- Saisie hors ligne indispensable (« ajout différé quasi tout le temps », synchronisation simple).
- Récupérer ses données ; open source.
- Idées : sous-groupes ou labels de membres, historique des modifications, stats d'évolution, prix enregistrés pour achats fréquents, lien vers une dépense, commande groupée complétée plus tard par chacun, OCR de ticket (pas prioritaire).

Critère de fin du chantier : le groupe importé depuis Tricount tourne en ligne, et une dépense ajoutée notifie les concernés (un Android, un iPhone) et pas les autres.

## Périmètre

- **Cible avant le lot 2** (répartie en plusieurs versions ; contenu de la version 1 : décision 10) : groupe sans compte (membres avec ou sans l'app, « qui je suis », invitation par lien) ; saisie rapide (un payeur, sélection accélérée des participants : dernière sélection, membres fréquents en tête, tout cocher ou décocher ; répartition égale, par parts, en montants exacts ; remboursements) ; saisie hors ligne avec file d'envoi ; ma part sur chaque ligne, filtre « me concerne », recherche par texte, payeur, participant, montant et date ; notifications aux seuls concernés, auteur exclu ; soldes, remboursements suggérés, vue par membre (moi contre le groupe) ; import Tricount, export complet ; PWA utilisable sur ordinateur, guide d'installation iPhone.
- **Lot 2** : sous-groupes de membres, commande groupée complétée par chacun, historique des modifications, lien vers une dépense, statistiques dans le temps.
- **Plus tard** : catégories (sauf usage intéressant trouvé), prix enregistrés, lecture des tickets, devises, pièces jointes. Idée de l'assistant, non retenue à ce jour : classement amical « qui sera la plus grosse pince ? » dans les stats.
- **Hors périmètre** : apps natives sur les stores, comptes utilisateurs, usage hors du groupe.
- Criticité : calcul des parts et des soldes (argent) ; import et soldes testés au centime contre Tricount.

## Lexique

- Workers : fonctions serverless de Cloudflare ; D1 : leur base SQLite gérée ; Time Travel : restauration de D1 à la minute près, 7 jours en offre gratuite ; workers.dev : sous-domaine gratuit fourni par Cloudflare.
- Web Push : notifications envoyées par le serveur au navigateur, signées par une paire de clés VAPID ; Hono et Drizzle : routeur HTTP et couche d'accès SQL en TypeScript.

## Ce qu'on sait

- **Alternatives** (`alternatives.md`, sous-agent, non contre-vérifié) : aucune app ne coche les contraintes ; aucune ne cible les notifications sans compte (`referentiel-fonctionnel.md`).
- **Usage réel du groupe** (`referentiel-fonctionnel.md`, script du 16/11 sur l'export, non contre-vérifié) : aucune dépense ne concerne les 13 membres, médiane 3 concernés, 49 dépenses ne concernant qu'une personne, payées par une autre ; 3 à 5 membres annexes ; 146 dépenses sur 236 à parts égales ; catégories, pièces jointes et devises quasi inutilisées.
- **Export Tricount** (vérifié le 16/11) : `export/lire_tricount.py` lit un groupe par le jeton de son lien, sans rattachement à un membre, par l'API non officielle de l'app Android. Le 16/11 le serveur refusait les anciennes versions d'app (HTTP 422 avec 7.0.7, version des exporteurs open source lus, et avec 14.6.1 ; signalé dans https://github.com/elrandar/tricount-api/issues/2) ; l'identifiant de la version 14.8.2, relu dans l'APK (classe UserAgentInterceptor), passe. Export en une page, le serveur ne signalant aucune page suivante (champ `Pagination` vide) : total des 236 dépenses 9 609,80 €, identique à l'app (confirmé par l'utilisateur) ; total des 14 remboursements (1 024,16 €) non recoupé ; sur l'export du 19/11, soldes et total des dépenses comparés à l'app, celui des remboursements recoupé indirectement (décision 45). L'export brut, avec les noms du groupe, reste hors de tout repo ; il se régénère avec le script et le jeton du lien. Fragile pour une synchronisation continue, suffisant pour migrer.
- **Bases open source** (`bases-open-source.md`) : Spliit (MIT, sans compte, sans notifications) et SplitPro (MIT, comptes, notifications ciblées) évalués ; page blanche retenue, Spliit sert de référence pour le calcul.
- **Notifications** (vérifié le 16/11, mesuré sur Workers le 19/11) : reçues dans Chrome sur un émulateur Android 15 avec Google Play, pas encore sur un vrai téléphone (`essais/android-notification-recue.png`, `essais/push-demo-server.mjs`) ; ciblage par « qui je suis » validé avec un Worker Cloudflare local et D1 (`essais/cloudflare/`). Sur Workers, le chiffrement de 9 notifications en un seul appel prend 10 à 16 ms de CPU, au-delà de la limite de 10 ms de l'offre gratuite, d'où l'envoi par une file (décision 46). Simulateur iOS : abonnement refusé, non concluant pour les vrais iPhone ; la doc Apple annonce le Web Push pour les apps web de l'écran d'accueil depuis iOS 16.4.
- **Hébergement** (`hebergement.md`, chiffres clés relus le 16/11) : Cloudflare D1 en juridiction UE garde ses réplicas dans l'UE ; Time Travel gratuit 7 jours ; offre gratuite : 100 000 requêtes par jour, 10 ms de CPU par requête, base de 500 Mo, 5 tâches planifiées, 50 requêtes SQL par invocation ; pas de gel des quotas garanti.
- **Nom** : repo GitHub `lou-theo/la-pince` créé et public (16/11) ; domaines lapince et la-pince en .fr, .com, .app, .eu pris ; adresse gratuite en sous-domaine workers.dev.

## Décisions

### Tranchées

1. **PWA** (16/11, dit par l'utilisateur) : installable, pas d'app native, « plus léger à développer et à gérer, surtout pour ceux sous iOS ».
2. **Sans compte** (16/11, dit par l'utilisateur) : chacun choisit qui il est ; certains membres n'ont pas le lien et d'autres saisissent pour eux en confiance. Coût si faux : quiconque a le lien peut se déclarer quelqu'un d'autre, comme dans Tricount.
3. **iPhone sur la foi de la doc Apple** (16/11, dit par l'utilisateur : « si c'est le cas faisons confiance ») : pas de test sur un vrai iPhone avant la mise en service.
4. **Répartition du travail** (16/11, dit par l'utilisateur) : « tu codes l'essentiel et je relis » ; architecture propre, tests à plusieurs niveaux.
5. **Page blanche plutôt que fork de Spliit** (16/11, dit par l'utilisateur) : Spliit fait environ 17 000 lignes hors tests et 58 dépendances, pour 527 lignes de cœur de calcul (commit `f293974`) ; algorithmes et cas de test repris sous licence MIT, cités. Références fonctionnelles multiples : Tricount pour la base, Sesterce, Spliit, toute autre app. Coût si faux : quelques jours d'interface (au jugé).
6. **Périmètre** (16/11) : section Périmètre ; hors ligne en première version, catégories en « plus tard », commande groupée au lot 2 (dit par l'utilisateur).
7. **Hébergement et stack** (16/11, dit par l'utilisateur) : Cloudflare Workers et D1 en juridiction UE, offre gratuite ; perte de la gratuité ou dépassement jugés peu probables, « on cherchera autre chose » ; pas de matériel à la maison, serveur loué « beaucoup trop cher ». Stack : TypeScript, PWA React avec Vite, IndexedDB et file d'envoi côté téléphone (identifiant unique créé sur le téléphone, envoi rejouable sans doublon), Hono et Drizzle côté serveur, SQLite (D1), Vitest et Playwright. Code portable vers un serveur Node si besoin.
8. **Nom** (16/11, dit par l'utilisateur) : « La Pince », surnom du groupe pour les radins ; slogan possible « Qui sera la plus grosse pince ? ».
9. **Saisie par montants en première version** (16/11, dit par l'utilisateur, retour du groupe) : saisir le montant de chacun sans total, le total se calcule ; total saisi qui ne correspond pas à la somme : enregistrement refusé. Les trois autres ajouts proposés (bascule « ma part / total », barre de répartition, emoji automatique) n'y entrent pas (« pas tout en 1ere version non ») ; ma part sur chaque ligne et soldes sont dans la version 1 (décision 10).
10. **Version 1** (18/11, proposée par l'assistant, acceptée par l'utilisateur : « la version 1 et possiblement plus loin va surtout être de la demo pour avoir des retours mais sans réel usage ») : démo, Tricount reste la référence jusqu'à la bascule du groupe, l'import se relance en écrasant le groupe. Contenu : import Tricount (soldes au centime) ; groupe par lien et « qui je suis », membres issus de l'import ; liste avec ma part sur chaque ligne, détail, soldes triés par montant, remboursements suggérés ; ajout, modification et suppression d'une dépense (un payeur, parts égales ou montants, tout cocher ou décocher) et d'un remboursement ; hors ligne (lecture en cache, file d'envoi, dernière modification arrivée au serveur gagnante) ; textes de l'interface prêts pour la traduction (i18n), pour ajouter d'autres langues sans reprise (demandé par l'utilisateur le 18/11), en français seul au départ (proposé par l'assistant). Le modèle porte dès la version 1 les parts inégales et les dépenses mêlant parts et montants (62 sur 236 dans l'import), seule leur saisie attend. Suite indicative, ordre à rediscuter : d'abord l'historique des modifications, première fonction annoncée après la version 1 (réponse du 19/11, décision 37) ; version 2 notifications aux seuls concernés et export complet, précédée de la mesure CPU sur Workers (compte Cloudflare à créer, doute à lever « assez rapidement », dit par l'utilisateur le 18/11) ; version 3 recherche, filtre « me concerne », vue par membre, puis bascule du groupe et guide iPhone ; ensuite sélections rapides, saisie par parts, invitation et ajout de membres, lot 2 ; plus tard, sans version fixée, une liste intégrée d'actions à trancher (conflit de modification, ajout échoué, dépense à compléter, décision 37).
11. **Modèle de données** (18/11, proposé par l'assistant, accepté par l'utilisateur) : montants en centimes entiers ; soldes recalculés à la volée, la performance étant « crucial[e] » et Tricount ne l'ayant pas été initialement (dit par l'utilisateur) ; Tricount sert à l'import, pas de modèle ; pour sortir d'une ligne par concerné (« on ne sera plus sur 1 ligne par concerné afin de pouvoir gérer certaines features », dit par l'utilisateur), la saisie (forme libre, versionnée, appelée à évoluer : lignes de reçu, frais communs ; une ligne par concerné pour démarrer) est séparée de son effet (payeur et part de chaque membre en centimes, forme fixe), seul lu par les soldes, le filtre, les notifications et les statistiques ; un seul type d'opération, un champ nature (dépense ou remboursement) servant seulement à l'affichage et aux statistiques, impossible à déduire (une avance pour un ami a la forme d'un remboursement). Remboursements saisis en dépenses dans Tricount : l'utilisateur pense que « plusieurs » l'ont été (18/11, non vérifié) ; sans effet sur les soldes, ils gonflent le total dépensé des statistiques.
12. **Synchronisation hors ligne** (18/11, proposée par l'assistant, acceptée par l'utilisateur) : chaque téléphone garde tout le groupe en local (environ 75 Ko par an, au jugé) et calcule tout ; saisies envoyées par une file rejouable, identifiant créé sur le téléphone ; le serveur recalcule l'effet avec le même cœur de calcul et refuse l'incohérent ; lecture incrémentale par un compteur croissant du serveur ; le serveur garde toutes les versions de chaque opération, la dernière arrivée gagne (jamais l'horloge du téléphone), l'historique permet de rattraper ; suppression par marquage. Modifications concurrentes d'une même dépense rares, l'usage étant des ajouts décorrélés (dit par l'utilisateur). Bibliothèques de fusion automatique (CRDT) écartées, non évaluées en détail.
13. **Organisation du repo** (18/11, proposée par l'assistant sur le modèle d'un monorepo organisé par domaines, acceptée par l'utilisateur) : monorepo ; `apps/app` (PWA), `apps/server` (Worker), `packages/core` (calcul, types, validation, conversion Tricount, sans dépendance aux autres), `packages/config` (configs partagées), `tools/import-tricount` (script local, passe par l'API de synchro de La Pince, le jeton ne quitte pas la machine) ; app et server dépendent de core, jamais l'un de l'autre. Contexte pour les agents : `AGENTS.md` (règles, carte du repo) avec `CLAUDE.md` réduit à `@AGENTS.md`, `CONTEXT.md` (glossaire, un terme défini une fois), `docs/architecture.md` (état et raisons, reprend les décisions 10 à 12 au premier code, pas d'ADR), `.claude/settings.json` et `.claude/skills/` ; rien créé « pour la structure ».
14. **Outillage** (18/11, proposé par l'assistant, ajusté par l'utilisateur) : pnpm avec catalogue de versions, Node épinglé ; TypeScript strict avec `noUncheckedIndexedAccess` ; ESLint rigoureux, règles publiques choisies et configurées pour le projet, dont les règles strictes de typescript-eslint (« un certain nombre de règles eslint custom me paraissent intéressantes, surtout si ça amène de la rigueur ») ; Prettier en largeur 150 (dit par l'utilisateur) ; zod pour toute donnée entrante, schémas dans core ; migrations Drizzle commitées et vérifiées ; pas de Turborepo au départ. Vérification avant push par un hook local (lefthook), qui lance tous les tests (demandé par l'utilisateur : « je ne payerai pas » de CI) ; GitHub Actions en filet, gratuit sans quota de minutes sur les runners standard d'un repo public (vérifié le 18/11 dans la doc GitHub : « The use of standard GitHub-hosted runners is free: […] In public repositories »).
15. **Stratégie de tests** (18/11, proposée par l'assistant, acceptée par l'utilisateur) : tests par l'interface publique, simulations seulement hors de notre code ; cinq niveaux : core (Vitest, cas de Spliit cités, tests de propriétés fast-check, couverture 100 %), serveur et base (runtime Workers local, vraie D1, migrations contrôlées sur le schéma et rejouées sur un jeu de données), app sans écran (file d'envoi, cache, IndexedDB simulée), bout en bout (Playwright, Chromium et WebKit, hors ligne puis synchro vers un second navigateur), performance (budgets en échec si dépassés). Corpus réel commité anonymisé (dit par l'utilisateur) : noms des membres remplacés, titres de dépenses inventés par l'assistant, dates réelles gardées, montants et répartitions intacts ; chaque effet recalculé comparé à celui de Tricount.
16. **Environnements de test** (18/11, proposé par l'assistant, accepté par l'utilisateur) : l'espace de test isolé est un groupe de démo, rempli du corpus anonymisé, isolé par son lien ; en développement, tunnel Cloudflare vers la machine pour tester sur un vrai téléphone en HTTPS (sans compte : supposé) ; version 1 sur un seul environnement en ligne ; à la bascule du groupe, une préproduction avec sa propre D1 (adresse de prévisualisation des versions Workers : supposé, à vérifier) ; pas de système d'environnements isolés par branche.
17. **Livraison par PR** (18/11, dit par l'utilisateur : repo à vocation open source) : jamais de push sur `main` (règle dans les consignes du projet) ; règle de branche GitHub proposée (PR obligatoire, 0 approbation, force-push et suppression interdits, aucune dérogation) créée le 18/11 sur go de l'utilisateur et relue active ; job de CI `verifier` requis depuis le squelette (décision 18) ; le repo fusionne déjà par squash seul, fusion automatique permise, branche supprimée après fusion. Avec le squelette : template de PR écrit pour le projet (Pourquoi, Ce que change, Impact sur le calcul, le schéma D1, le contrat de synchro ou les données du téléphone, Vérification avec visuels ; pas de checklist, doublon de la CI et du lint, la règle des données identifiables portée par un commentaire d'en-tête, décidé le 18/11 par l'utilisateur). Avec les premiers écrans : script de captures dans le repo (`pnpm captures`, Playwright : planche avant/après en format téléphone et ordinateur, GIF pour un parcours) et skill `captures` versionné dans `.claude/skills/` qui dit quand et comment s'en servir (18/11, dit par l'utilisateur), signalé dans `AGENTS.md` pour les autres agents ; outil écrit pour le projet, sans reprise de code tiers ; données de démo anonymisées seulement (les images d'une PR publique sont publiques). Les skills de workflow (`/chantier`, `/revue`, `/livrer`) restent personnels, hors du repo.
18. **Squelette** (18/11, plan proposé par l'assistant, go de l'utilisateur) : `packages/config` et `packages/core` seuls, `apps/` et `tools/` créés avec leur premier code ; `core` porte dès le squelette un vrai module, la conversion d'un montant saisi en centimes (schéma zod, refus plutôt qu'arrondi, plafond 99 999 999,99 €), pour que la CI éprouve lint, typecheck et couverture 100 % sur du code d'argent (alternatives écartées : squelette sans code, CI à vide ; squelette et cœur en une seule PR, trop gros à relire). Choix de l'assistant pendant le code : TypeScript 6.0 et non 7, que typescript-eslint ne prend pas encore en charge (dépendance limitée à `<6.1.0`, lu dans npm le 18/11) ; versions publiées depuis plus d'un jour seulement (réglage par défaut de pnpm 11) ; frontières entre paquets par les dépendances déclarées, contrôlées par la règle ESLint `import-x/no-extraneous-dependencies` (pnpm seul laisse importer les outils de la racine) ; `curly` remise après `eslint-config-prettier`, qui l'éteint ; condition sur un nombre ou une chaîne interdite par ESLint (0 centime pris pour une absence), `parseFloat` et `toFixed` interdits dans `core` ; Prettier hors des règles ESLint (`eslint-config-prettier`, vérifié à part) ; `.claude/settings.json` reporté, sans contenu utile à ce jour ; docs de cadrage reformatées par Prettier (alignement des tableaux), contenu inchangé. Coût si faux : configuration à reprendre, sans effet sur le calcul.
19. **Centime restant et import** (18/11, proposé par l'assistant, accepté par l'utilisateur) : le centime restant d'une répartition suit la règle de Spliit (plus grand reste, égalité départagée par une rotation tirée de l'identifiant de l'opération), seule règle du cœur ; l'import enregistre les parts calculées par Tricount comme une saisie en montants exacts, identiques au centime par construction. Raison : Tricount suit sa propre règle (sur les 250 opérations de l'export, 36 ont un centime restant, donné aux dernières lignes de la liste dans 31 cas, règle non identifiée dans 5 ; script local du 18/11, non contre-vérifié). Alternatives écartées : saisie en poids avec un champ « centimes restants attribués à » rempli par l'import (garde les dépenses importées modifiables à parts égales, au prix d'un champ de plus à valider) ; imiter la règle de Tricount (cas inexpliqués, calcul dépendant d'un concurrent). Coût si faux : une dépense importée à parts égales s'ouvre en montants à la modification et se remet à parts égales à la main.
20. **Remboursements suggérés** (18/11, proposé par l'assistant, accepté par l'utilisateur) : algorithme glouton de Spliit (créanciers puis débiteurs, dans un ordre fixe par identifiant), stable : un virement suggéré une fois fait laisse les suivants inchangés, quel que soit l'ordre dans lequel les membres remboursent. Sur les soldes de l'export du 16/11 (13 membres à solde non nul, dans l'ordre des identifiants Tricount ; le nombre dépend de cet ordre ; l'import garde les identifiants de Tricount, le corpus de démo en a d'autres, décision 26), 12 virements contre 11 pour le plus gros créancier contre le plus gros débiteur d'abord et pour le minimum exact (script local du 18/11, non contre-vérifié), deux alternatives écartées pour leur instabilité. Coût si faux : un virement de plus que le minimum, algorithme isolé et remplaçable.
21. **Langue du code** (18/11, proposé par l'assistant, accepté par l'utilisateur) : code en anglais (noms, commentaires, intitulés de tests), pour ne pas fermer le projet aux contributeurs non francophones ; docs, messages de commit et descriptions de PR en français, lus par le mainteneur ; `CONTEXT.md` donne pour chaque terme du domaine son nom dans le code, la doc citant l'identifiant entre accents graves. Alternatives écartées : tout en français (domaine lu sans traduction, mais code fermé aux non-francophones), tout en anglais (doc à lire en anglais sans besoin à ce jour). Coût si faux : renommage, d'autant plus cher que le code grandit.
22. **Nature et statistiques** (18/11, proposé par l'utilisateur pendant la revue) : l'effet porte un booléen `countsAsSpending` (compte dans le total dépensé), décidé par chaque version de saisie (version 1 : vrai pour une dépense, faux pour un remboursement) ; la nature reste dans la saisie, pour l'affichage. Les statistiques ne lisent ainsi que l'effet, et une forme de saisie future (avance, correction) peut se sortir des statistiques sans toucher à leur code. Alternatives écartées : nature portée par l'opération, hors saisie (règle d'exclusion dans le code des statistiques) ; nature recopiée dans l'effet (donnée d'affichage mêlée aux comptes). Coût si faux : un seul booléen pour toutes les statistiques ; un autre découpage demandera un champ de plus dans l'effet.
23. **Avancée en autonomie** (19/11, proposé par l'assistant, accepté par l'utilisateur : « oui ça me semble bien », points à trancher « idéalement en amont ») : l'agent fusionne lui-même ses PR qui avancent le plan, CI verte et revue faite, choix techniques et d'interface de la démo compris (« les choix d'interface de la démo » faisaient partie du périmètre accepté), et pose les points à trancher de préférence avant le code de chaque étape, sans coder ce qui en dépend avant la réponse ; correctifs et outillage que le plan demande compris, toute autre PR attendant le mainteneur (ajout de l'assistant) ; arrêts listés dans `AGENTS.md` (accès extérieurs, mise en ligne et données réelles, périmètre ou retour du groupe, décision à rouvrir ; la mise en ligne du code n'en est plus un depuis la décision 43). Précise la décision 4 : le mainteneur relit ces PR quand il veut, après fusion (« tu relis quand tu veux et tu rouvres ce qui ne te va pas », proposé par l'assistant et accepté). Raison : la version 1 est une démo, Tricount reste la référence (décision 10), une erreur fusionnée coûte une PR de correction. Coût si faux : une erreur arrive sur `main` sans relecture humaine, la CI requise et la revue adversariale restant en place.

27. **Contrat de synchronisation** (19/11, choix de l'assistant en autonomie, décision 23, sur le plan de l'étape 5) : le contrat vit dans `packages/core` (`operationSchema`, `operationBatchSchema`, `operationBatchResponseSchema`, `changesQuerySchema`, `changesResponseSchema`, `groupResponseSchema`, `adminGroupSchema`, `apiErrorSchema`), pour que l'app et le serveur ne recopient aucun schéma. 28. **Route d'administration et ré-import** (19/11, arbitrage pris en autonomie, décision 23 ; complète la décision 13) : `PUT /api/admin/groups/:id`, sous le secret `ADMIN_TOKEN`, crée ou met à jour le titre, le jeton du lien et les membres d'un groupe, la synchronisation ne créant ni groupe ni membre en version 1 (décision 10) ; les opérations passent par l'API de synchronisation (décision 13). Un membre absent du corps est gardé, des opérations pouvant le nommer ; un jeton du lien déjà pris par un autre groupe est refusé (`409 token_in_use`). L'identifiant du groupe est celui du tricount, pour qu'un ré-import écrase le même groupe ; le jeton du lien, tiré par l'outil d'import, fait de 32 à 128 caractères parmi lettres ASCII, chiffres, `-` et `_` ; le secret passe dans l'en-tête `Authorization: Bearer`. Le ré-import écrase le groupe (décision 10) : une opération absente de l'export est marquée supprimée, y compris une opération créée dans La Pince ; un import identique ne crée aucune version ; une opération modifiée dans Tricount en crée une, son identifiant de version tiré d'un haché du groupe, du contenu et de la version courante, c'est-à-dire le `seq` courant de l'opération, ou rien si elle est absente (SHA-256 en hexadécimal : 64 caractères, la longueur maximale d'un identifiant ; le contenu seul ferait prendre pour un renvoi un retour à un état antérieur). L'outil d'import lit les changements depuis 0, compare et envoie : le serveur n'offre rien de plus. Alternatives écartées : création du groupe par la synchronisation (hors version 1) ; import écrit directement en base (deux chemins d'écriture). Coût si faux : le secret d'administration donne la main sur tous les groupes, à remplacer si des groupes se créent depuis l'app.

30. **Choix du serveur** (19/11, choix de l'assistant en autonomie, décision 23, sur les arbitrages du 19/11) : (a) chaque version d'un lot reçoit son résultat : écrite avec son `seq`, renvoi (`duplicate`), ou refusée avec son motif (`invalid_operation`, `unknown_member`, `operation_in_other_group`, `revision_conflict`) ; le lot entier n'est refusé que pour un corps illisible, une enveloppe hors schéma ou une version sans identifiant lisible, à laquelle on ne peut pas répondre ; la file d'envoi retire une version dans les trois cas, pour qu'aucune ne bloque les suivantes ; (b) une version et l'état courant de son opération s'écrivent dans un seul lot D1, qui est une transaction, les gardes vivant dans les instructions : la version n'est insérée que si son opération n'appartient pas à un autre groupe, l'état courant ne bouge que si la version vient d'être insérée (`changes()`), et une version prise par une requête concurrente entre la lecture et l'écriture est rejugée sur une lecture fraîche ; ces deux écritures sont en SQL, le lot D1 de Drizzle ne prenant pas une instruction SQL libre, et leurs noms de tables et de colonnes suivent `schema.ts` ; (c) un identifiant d'opération appartient à un seul groupe sur tout le serveur ; (d) le jeton du lien est gardé haché (SHA-256), et le secret d'administration comparé par hachés ; (e) un curseur au-delà du dernier `seq` du groupe reçoit `409 cursor_ahead`, et le téléphone relit depuis 0 ; (f) une version est gardée en JSON aux clés triées et comparée telle quelle ; l'effet n'est pas stocké, chaque téléphone le recalcule, et le serveur refuse une saisie incohérente par le schéma de saisie ; (g) versions publiées depuis plus d'un jour, tenues dans le catalogue de `pnpm-workspace.yaml` (drizzle-kit reste en 0.x, la 1.0 étant en préversion) ; les scripts d'installation d'esbuild et de workerd ne sont pas lancés, leur binaire venant de leur paquet de plateforme. Alternatives écartées : refus du lot entier pour une version fautive (bloque la file d'envoi) ; lecture puis écriture sans garde (sous concurrence, une ancienne version écraserait la récente). Coût si faux : (b) du SQL à tenir d'accord avec le schéma Drizzle, couvert par les tests de `store.ts` ; (e) un serveur reconstruit qui a dépassé le curseur d'un téléphone ne se signale pas, le téléphone gardant des opérations disparues.

# Édition du groupe : serveur et contrat

25/11/2026, pris par l'assistant en autonomie, décision [Avancée en autonomie](avancee-en-autonomie.md), sauf le point f, tranché par le mainteneur ; étape 13, point b.

- (a) **lecture tolérante, écriture stricte** : le schéma de lecture du groupe et de ses membres (`groupResponseSchema`, `memberSchema`) retire un champ inconnu au lieu de refuser la réponse ; ce que le serveur accepte reste strict (route d'administration sur la même forme, corps des routes nouvelles) ; tout champ ajouté plus tard à une lecture est facultatif ; seule une app chargée depuis ce changement en profite : une app plus ancienne restée ouverte tombe en erreur de lecture à la première photo, jusqu'à son prochain lancement ([architecture](../architecture.md), section App, puce PWA), d'où ce changement livré bien avant le point d de l'étape 13 ; raison : le code se déploie à chaque fusion (décision [Déploiement à chaque fusion](deploiement-continu.md)) et un téléphone garde l'ancienne app chargée, que la photo du point d de l'étape 13 ferait échouer en `unexpected`, et la copie IndexedDB repasse par ce schéma, effacée s'il refuse ; écarté : un numéro de version du contrat (deux versions à servir) ; coût si faux : un champ mal formé côté serveur passerait inaperçu, sans effet tant qu'il n'est pas lu
- (b) **trois routes sous le jeton du lien**, sans secret d'administration, chacune répondant le groupe entier (comme `GET`), pour que le téléphone affiche ce que tient le serveur : `PATCH /api/groups/:token` (`{ title }`), `POST /api/groups/:token/members` (`{ id, name }`, 201 si créé), `PATCH /api/groups/:token/members/:id` (`{ name }`, corps strict d'au moins un champ, extensible) ; erreurs `400 invalid_request`, `404 group_not_found`, `404 member_not_found` (membre inconnu ou d'un autre groupe), `409 too_many_members`, `409 member_name_taken` ; écarté : passer l'édition par la file d'envoi des opérations (décision [Édition du groupe et avatar](edition-du-groupe.md), point h : en ligne seulement)
- (c) **identifiant du nouveau membre tiré par le téléphone** (`memberIdSchema`), une fois à l'ouverture de la feuille d'ajout et renvoyé à chaque nouvel essai : une requête rejouée après une réponse perdue trouve le membre et répond 200 avec le groupe tel quel, nom inchangé même renommé entre-temps, même dans un groupe plein ; écarté : identifiant tiré par le serveur (un essai après une réponse perdue créerait un doublon)
- (d) **plafond de 100 membres** (`MAX_GROUP_MEMBERS`), aligné sur le nombre maximal de lignes d'une saisie, pour qu'une dépense puisse encore concerner tout le monde ; la route d'administration n'est pas plafonnée ; coût si faux : un chiffre à changer
- (e) **concurrence sans migration** : une édition de membre lit les membres du groupe en une valeur (identifiants et noms en JSON, par identifiant), les juge (plafond, nom pris), puis écrit par une seule instruction qui ne passe que si cette valeur n'a pas changé ; sinon elle relit et rejuge, dix essais au plus, chacun perdu parce qu'une autre édition du groupe est passée ; l'ajout calcule sa position (`MAX(position) + 1`) dans la même instruction `INSERT … SELECT … ON CONFLICT DO NOTHING` ; D1 exécute les instructions d'une base l'une après l'autre ; deux ajouts simultanés prennent donc deux positions distinctes, et deux ajouts du même nom n'en créent qu'un ; la course est jouée dans les tests par une lecture prise avant une écriture concurrente, et la garde retirée les fait échouer ; `readGroup` trie par position puis identifiant, car la route d'administration calcule encore ses positions sur une lecture antérieure et peut en donner une déjà prise par un ajout simultané ; écartés : une contrainte d'unicité en base sur le nom normalisé (migration, et le `lower()` de SQLite ne couvre que l'ASCII), garde sur le seul nombre de membres (ne voit pas un renommage) ; coût si faux : une requête en échec sous un flot d'éditions du même groupe
- (f) **nom en double refusé** (tranché par le mainteneur le 25/11 : « ok avec reco, les noms doivent etre unique ») : `409 member_name_taken` à l'ajout comme au renommage quand un autre membre du groupe porte le même nom, comparé par `memberNameKey` du cœur (NFC, caractères que l'écran ne dessine pas et espaces de bord retirés, minuscules `fr-FR` ; une espace sans chasse ou un liant d'emoji ne suffit pas à distinguer deux noms identiques à l'œil), que l'app reprend pour griser un nom pris ; renommer un membre en son propre nom, casse changée comprise, reste permis ; ni la route d'administration ni le schéma de lecture ne refusent un doublon (un import peut en porter) ; écarté : accepter les doublons (deux « Paul » indiscernables dans les listes)
- (g) **textes saisis** : espaces de bord retirés puis validés, caractères de contrôle refusés, au moins un caractère visible exigé (`enteredTextSchema`) ; bornes inchangées (50 pour un nom, 100 pour un titre) ; le schéma de lecture, la route d'administration et `textSchema` gardent leurs règles, pour relire ce que l'import a déjà écrit
- (h) **dernière écriture gagnante** pour deux renommages concurrents, comme pour les opérations (décision [Synchronisation hors ligne](synchronisation-hors-ligne.md)) ; aucune notification pour un ajout ou un renommage
- (i) **ré-import** (décision [Édition du groupe et avatar](edition-du-groupe.md), point f) : un membre ajouté dans l'app garde sa place, le titre et les noms de l'export réécrivent ceux de l'app ; un membre ajouté dans l'app et présent aussi dans Tricount sous un autre identifiant donne deux membres au ré-import, celui de l'app à solde nul et sans retrait possible : accepté, le ré-import ne servant qu'avant la bascule
- (j) **base restaurée** : un membre ajouté après l'instant restauré est perdu, comme une opération (décision [Détection d'une base restaurée](base-restauree.md)), et une opération qui le nomme, renvoyée par une file d'envoi, est refusée (`unknown_member`)
- (k) **comment l'app apprend qu'une instance a un espace KV** : par `photos: true` dans la réponse du groupe (décision [Photos des membres : stockage et contrat](photos-stockage.md), point f).

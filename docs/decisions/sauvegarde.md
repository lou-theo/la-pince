# Copie quotidienne de la base

19/11/2026, mécanisme proposé par l'assistant et accepté ; point b changé à la demande de l'utilisateur le 19/11.

- (a) Time Travel couvre 7 jours sans réglage (constaté le 19/11 : la base distante rend des points de restauration pour des instants passés) ; au-delà, une tâche planifiée GitHub Actions (`tools/sauvegarde/sauvegarde.yml`, modèle copié dans un repo privé à soi, jamais lancé depuis le repo public) exporte la base chaque jour (planifiée la nuit, lancée par GitHub en journée, constaté du 20 au 24/11) et commite la copie seulement si l'export a changé (deux exports d'une base inchangée sont identiques, constaté le 19/11), l'historique du repo donnant la base à toute date passée
- (b) copie compressée puis chiffrée par `age` vers une clé publique, secret `AGE_RECIPIENT` du repo privé, la clé privée gardée dans le gestionnaire de mots de passe du mainteneur et jamais dans un fichier (dit par l'utilisateur : « je change d'avis sur la décision [Copie quotidienne de la base](sauvegarde.md), point b du cadrage : copie chiffrée, plus en clair ») ; deux chiffrements du même export diffèrent (constaté le 19/11), si bien que le changement se détecte sur l'empreinte SHA-256 de l'export en clair, commitée à côté avec la clé publique utilisée (une clé changée rechiffre la copie), l'empreinte ne permettant que de confirmer une base entière déjà détenue ; la copie en clair d'avant a été retirée de l'historique du repo privé par force-push, les commits orphelins restant lisibles par leur SHA sur GitHub jusqu'à un nettoyage par son support, que rien ne déclenche seul (choisi par l'utilisateur : « rien de sensible en l'état, c'est surtout pour faire propre », la copie ne portant que le groupe de démo)
- (c) jeton Cloudflare réservé à la sauvegarde, avec le seul droit D1 en écriture (l'export est refusé à un jeton en lecture, constaté le 19/11), pour que GitHub ne garde pas celui du déploiement, qui publie aussi le Worker
- (d) une copie se restaure dans une base neuve vers laquelle l'instance bascule, l'ancienne gardée ; l'export rejoué dans une D1 locale, puis dans une base D1 neuve sur Cloudflare, redonne les mêmes nombres de versions et d'opérations et le même compteur `sqlite_sequence` (constaté le 19/11 sur le groupe de démo, copie encore en clair), dont dépend la détection d'une base restaurée (décision [Détection d'une base restaurée](base-restauree.md)) ; une copie chiffrée, déchiffrée par `age -d -i -` avec la clé lue dans le presse-papiers sans fichier, redonne l'export à l'octet près et, rejouée dans une D1 locale, les mêmes nombres que la base en ligne (constaté le 19/11) ; la config de l'instance garde `database_name` à `la-pince` et ne change que `database_id`, le déploiement et Time Travel trouvant la base par ce nom.

Alternatives écartées : copie en clair (retenue d'abord, les jetons des liens n'y étant que hachés, décision [Partage du lien du groupe](partage-du-lien.md) ; écartée par l'utilisateur) ; tâche sur la machine du mainteneur (ne tourne que machine allumée, pas reprenable par un autre groupe) ; tâche du Worker vers R2 (reste chez Cloudflare, donc ne protège pas de la perte du compte, et R2 demande une carte) ; fichiers attachés à une exécution dans le repo public (gardés 90 jours au plus, téléchargeables par tout compte GitHub).

Coût si faux : une copie qui échoue sans que personne lise le mail de GitHub laisse la base sans copie au-delà de 7 jours ; la clé privée perdue, aucune copie ne se restaure ; le repo grossit de la copie entière à chaque jour de changement, un fichier chiffré ne se stockant pas en différentiel.
